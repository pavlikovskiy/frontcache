# Frontcache 2.13.0-RC — release note

Docs index: [../doc-index.md](../doc-index.md) · All release notes: [README.md](README.md)

Everything that has landed since 2.12.0:

- **The console can call some edges with a key of their own.** A new optional `edges` list in
  `frontcache-console.conf`, beside `urls`:

  ```hocon
  frontcache.console {
    urls   = ["https://fc1.example.com/", "https://fc2.example.com/"]
    apiKey = "<the edges' key>"
    edges  = [ { url = "https://origin.example.com/", apiKey = "<the origin's key>", label = origin } ]
  }
  ```

  Each `edges` entry is called with its own `apiKey`, never the console-wide one, and the console-wide
  key is never sent to it - for a console that watches nodes of two key domains, an edge tier and the
  filter inside an origin application, say. Entries come after `urls` on every screen; the Edges screen
  shows them (with their `label`) and does not remove them, and never adds one of their URLs to `urls`.
  The list is read whole or refused whole: an entry without `url` or `apiKey`, an unknown key, or a URL
  that is in `urls` too or twice in `edges` stops the console at startup, with a message that never
  quotes a key. Nothing changes for a config without `edges`.

- **The console's realtime page reads `/fc-dashboard.stream`, no longer `/hystrix.stream`.** Every node since
  2.7 serves the stream at both paths, and still does - `/hystrix.stream` stays on the node for external
  Hystrix Dashboard / Turbine readers. What to check before upgrading the console:
  - a reverse proxy, firewall or `guard-rules.conf` in front of a node must admit the console to
    `/fc-dashboard.stream` and must not buffer it (the [front-door example](../../examples/front-door/README.md)
    and the install guide's nginx recipe already cover both paths). A rule naming only `/hystrix.stream` leaves
    that node's card empty, with no error on the page - the console logs the relay's failure.
  - a 2.6 node (or older) serves only `/hystrix.stream`, so its realtime card is empty on this console;
    its other screens are unchanged.

  A proxy URL that names the edge with either path (`/fc-dashboard-proxy.stream?origin=<edge>/hystrix.stream`)
  still resolves to that edge.

- **Plugins: a plugin API, a manifest, and events after the fact.** A node's extension point, the module SPI of
  2.11.0, is now a plugin SPI with its own small artifact, `org.frontcache:frontcache-plugin-api` (interfaces and
  value types only, compiled against `compileOnly`; every node carries it through `frontcache-core`). Nothing
  changes for a node without plugins - it serves, logs and exports exactly what it did, and `get-node-stats`
  reports an empty `plugins` list. For whoever writes or installs one:
  - **A plugin is found by its manifest**, `META-INF/frontcache-plugin.properties` in its jar (`id`, `class`,
    `version`, `plugin-api = 1`, `kinds`, optional `name` / `vendor` / `license` / `config`), and its jar sits
    where `frontcache-core` does: the server war's `WEB-INF/lib`, or a filter-mode application's class path. A
    `.properties` file has no trailing comments - everything after `=` is the value.
  - **The kinds are declared, then checked.** This release offers `observe` (events) and `manage` (lifecycle,
    management actions, meters). A manifest that declares another kind, another `plugin-api` major or an id
    already taken, a class that cannot be loaded, a plugin that throws in `start`, and one that contributes
    something of a kind it did not declare are each logged and reported - and **the node starts without that
    plugin**.
  - **`observe` plugins receive events after the fact**, on a thread and a bounded queue of their own
    (`front-cache.plugins.<id>.queue`, default 10,000; a full queue drops and counts): `GuardMatched`
    (a rule rejected, redirected, or matched as a dry run), `RateLimitExceeded` (once per client and window, not
    once per refusal), `GuardSummary` (every 10 s: matches per rule, clients over the limit per bucket),
    `CircuitStateChanged`, `ConfigReloaded` (`guard-rules.conf`, `bots.conf`, `resilience.properties`) and
    `PluginStateChanged`. A node nobody observes builds no event. Events never carry a cookie value,
    `Authorization`, the API key or a request body; the rate limiter's client address is carried, and
    `PluginContext.hashClientKey` is how a plugin sends it on without disclosing it.
  - **Visible**: `get-node-stats` has `plugins` - each plugin's manifest facts, `state` (`started`, `failed`,
    `refused`, `stopped`) with the reason, and its delivered / dropped event and error counts - beside the
    older `modules` (the started ids). `/fc-metrics` exports `frontcache_plugin_state`,
    `frontcache_plugin_errors_total` and `frontcache_plugin_events_dropped_total` per plugin; a node without
    plugins exports none of them.
  - **For a 2.11 / 2.12 module**: `org.frontcache.module` is deprecated. A `FrontcacheModule` with only its
    `META-INF/services` file still runs, as a `manage` plugin, with a WARN at start - for one release. Move it
    to `org.frontcache.plugin.FrontcachePlugin` and give it a manifest. `ActionResponse` moved into
    `frontcache-plugin-api` with its package unchanged, so code using it compiles as before.
